  rr_index   int NOT NULL DEFAULT 0,
  flip_count int NOT NULL DEFAULT 0          -- für eigene Debug-Zwecke
);

BEGIN
  UPDATE subject_state s
     SET rr_index = (s.rr_index + 1) % (SELECT count(*) FROM state_catalog),

END; $$ LANGUAGE plpgsql

Machbarkeitsanalyse: Manipulation von Polizeidatenbanken durch privilegierte Datenbankzugriffe

Deine Frage lässt sich als Informatik- und Sicherheitsanalyse untersuchen, ohne behaupten zu müssen, dass ein solcher Mechanismus in einer Schweizer Polizeidatenbank tatsächlich existiert. Ich trenne deshalb drei Ebenen:

    Technische Machbarkeit: Kann eine Datenbank beim Zugriff auf einen bestimmten Personendatensatz automatisch dessen Inhalt verändern?

    Systemarchitektur und Berechtigungen: Welche Möglichkeiten hat ein Datenbankadministrator gegenüber einem Zugriff über das reguläre Frontend?

    Erkennbarkeit und Auswirkungen: Wie könnte eine solche Veränderung zu widersprüchlichen Informationen führen, und welche technischen Gegenmassnahmen gibt es?

Dein vorgeschlagener Mechanismus ist grundsätzlich mit bekannten Datenbanktechniken verwandt: Trigger, gespeicherte Prozeduren, zustandsbehaftete Logik und Round-Robin-Auswahl. Eine wichtige Unterscheidung besteht allerdings zwischen einer technisch möglichen Manipulation und dem Nachweis, dass eine solche Manipulation in einer konkreten Behörde stattfindet.

Eine Einschränkung beim Proof of Concept: Ich kann den Mechanismus in einer isolierten Testdatenbank demonstrieren und seine Grösse abschätzen. Ich werde dafür aber keine Prozedur konstruieren, die gezielt reale Personen in Polizei- oder Fahndungsdatenbanken bei jedem Zugriff mit wechselnden, potenziell folgenreichen Verdachtskategorien versieht. Das wäre nicht mehr nur eine Demonstration von Datenbanktechnik, sondern ein unmittelbar übertragbares Muster zur Manipulation behördlicher Personenakten. Für die Machbarkeitsanalyse braucht es diesen Schritt nicht: Wir können die Zustandsmaschine, den Trigger, die Transaktion und die Grössenordnung mit neutralen Testdaten untersuchen.

Was bedeutet das für deinen Angriffspfad?

Man kann ihn als hypothetische Kette modellieren:

1. Privilegierter Datenbankzugriff

Ein Benutzer oder Dienst besitzt weitreichende Berechtigungen.

2. Zugriffserkennung

2. Könnte ein Datenbankadministrator am Frontend vorbei zugreifen?

Ja. Das ist eine normale Möglichkeit in Datenbankarchitekturen, sofern die entsprechenden Netzwerkzugänge und Berechtigungen vorhanden sind.

Ein GUI ist üblicherweise ein Client, der Daten über eine Anwendungsschnittstelle oder direkt über einen Datenbanktreiber abfragt. Ein autorisierter Administrator kann unter Umständen einen SQL-Client verwenden und dieselben Datenbankobjekte direkt ansprechen.

Es sind dabei drei unterschiedliche Protokollierungsebenen zu unterscheiden:

    Anwendungsprotokoll: Was das GUI oder der Anwendungsserver als Benutzeraktion registriert.

    Datenbankprotokoll: Welche Verbindungen, SQL-Anweisungen oder Datenänderungen der Datenbankserver protokolliert.

    Unabhängige Überwachung: Welche Ereignisse ein separates Audit-System oder eine externe Sicherheitskomponente erfasst.

Ein direkter Zugriff kann Anwendungsprotokolle umgehen, die ausschliesslich im GUI entstehen. Daraus folgt jedoch nicht, dass er keine Datenbank- oder Betriebssystemprotokolle hinterlässt.

Ebenso wichtig ist die Gegenrichtung: Ein Datenbankadministrator mit weitreichenden Rechten kann möglicherweise die Datenbankkonfiguration, Trigger oder bestimmte Protokollmechanismen verändern. Wie weit diese Befugnisse reichen, hängt vom konkreten System ab. Ein Datenbankadministrator ist nicht automatisch auch Administrator des Betriebssystems, der zentralen Protokollplattform oder aller Sicherungssysteme.

Die Sicherheitsfrage lautet deshalb nicht nur: „Kann ein Administrator direkt zugreifen?“, sondern auch: Welche unabhängigen Kontrollinstanzen bleiben ausserhalb seines administrativen Einflussbereichs?

     WHERE id = 1;

Die Datenbank-Engine setzt dabei Grenzen. PostgreSQL führt Triggerfunktionen innerhalb der auslösenden Transaktion aus. MySQL hat unter anderem Einschränkungen bezüglich der Anweisungen, die innerhalb von Triggern oder gespeicherten Funktionen ausgeführt werden dürfen.

6. Das Problem mit mehreren gleichzeitigen Zugriffen

Ein einfacher Round-Robin-Zähler sieht zunächst trivial aus. Sobald zwei oder mehr Benutzer gleichzeitig zugreifen, entstehen jedoch Synchronisationsfragen.

Angenommen, der Zustand ist 0. Zwei Transaktionen lesen gleichzeitig diesen Zustand und versuchen, ihn auf 1 zu erhöhen. Je nach Implementierung können sie sich gegenseitig blockieren, denselben Folgezustand berechnen oder zu einem anderen Ergebnis kommen als erwartet.

Eine korrekte Implementierung muss daher festlegen:

    ob jeder Zugriff einen eigenen, atomaren Zustandswechsel darstellt;

    ob Zugriffe serialisiert werden;

    ob ein fehlgeschlagener Zugriff den Zustand trotzdem verändert;

    ob ein Rollback auch den Zustandswechsel rückgängig macht;

    ob die Zustände pro Datensatz, Sitzung, Benutzer oder global geführt werden.

Das ist keine theoretische Spitzfindigkeit. Es entscheidet darüber, ob ein solcher Mechanismus reproduzierbar funktioniert oder bei hoher Zugriffslast inkonsistente Ergebnisse liefert.

Bei deinem hypothetischen Szenario wäre zusätzlich zu klären, was überhaupt als „Zugriff“ zählt: eine SQL-Anweisung, ein gelesener Datensatz, ein GUI-Aufruf oder eine erfolgreiche Anzeige. Das sind unterschiedliche Ereignisse.
7. Der wesentliche Unterschied: Gespeicherte Daten ändern oder nur Ergebnisse variieren

Für deine Recherche ist das eine besonders wichtige Unterscheidung. Es gibt mindestens drei verschiedene Modelle:

Modell A – persistente Veränderung

Die zugrunde liegende Tabellenzeile wird geändert. Nachfolgende Abfragen können den veränderten Wert lesen. Das ist eine tatsächliche Datenänderung.

Modell B – wechselnde Darstellung

Die gespeicherten Daten bleiben gleich, aber eine Zugriffsschicht liefert unterschiedliche Darstellungen oder zusätzliche Informationen. Eine Abweichung im Frontend wäre dann nicht automatisch eine Änderung der ursprünglichen Daten.

Modell C – unterschiedliche Datenquellen

Verschiedene Anwendungen, Replikate oder Caches liefern unterschiedliche Versionen. Das kann auch ohne absichtliche Manipulation passieren.

Diese Modelle haben unterschiedliche technische Ursachen und müssen mit unterschiedlichen Tests untersucht werden.
8. Wie liesse sich das bei einer realen Datenbankarchitektur untersuchen?

Ohne auf die Frage einzugehen, wie ein Administrator Kontrollen umgehen könnte, lässt sich eine belastbare Prüfung auf mehrere voneinander unabhängige Bereiche verteilen.

Prüfbereich
	

Technische Frage

Schema und Metadaten
	

Welche Trigger, Funktionen, Prozeduren und Views sind tatsächlich definiert?

Berechtigungen
	

Welche Rollen dürfen Tabellen, Funktionen und Datenbankschemata verändern?

Änderungsnachweis
	

Gibt es nachvollziehbare Vorher-Nachher-Versionen der Datensätze?

Unabhängiges Audit
	

Werden Zugriffe und Änderungen zusätzlich ausserhalb der administrierten Datenbank erfasst?

Sicherungen
	

Lassen sich gespeicherte Datenstände aus unabhängigen Backups vergleichen?

Replikation
	

Stimmen die relevanten Daten zwischen Primärsystem und Replikaten überein?

Anwendungsebene
	

Entspricht das angezeigte Ergebnis den gespeicherten Quelldaten?

Eine solche Untersuchung kann feststellen, welche technischen Möglichkeiten vorhanden sind und ob konkrete Abweichungen nachweisbar sind. Sie kann allein aus der Existenz eines privilegierten Administratorkontos jedoch nicht ableiten, dass eine Manipulation vorgenommen wurde.

Für einen belastbaren Nachweis wären konkrete Artefakte nötig: beispielsweise unterschiedliche Datenstände, Schemaänderungen, nachvollziehbare Änderungsereignisse oder reproduzierbare Abweichungen zwischen einer unabhängigen Sicherung und dem aktuellen Datenbestand.

Ein fehlender Eintrag in einem einzelnen Protokoll beweist weder, dass kein Zugriff stattgefunden hat, noch, dass eine Manipulation stattgefunden hat.
9. Zu deiner Motivationsthese: Verwirrung durch wechselnde Verdachtskategorien

Deine drei Beispielzustände unterscheiden sich nicht nur technisch, sondern auch in ihrer möglichen Wirkung auf die Interpretation einer Personenakte.

Ein wechselndes Etikett könnte hypothetisch dazu führen, dass verschiedene Bearbeiter widersprüchliche Informationen sehen oder dass spätere Entscheidungen auf einer falschen Annahme beruhen. Die tatsächlichen Folgen hingen jedoch davon ab, ob diese Felder überhaupt für Entscheidungen verwendet werden, ob sie als verbindlich gelten und ob andere Datenquellen sie bestätigen.

Dabei sind zwei Hypothesen auseinanderzuhalten:

    H1 – technische Möglichkeit: Eine privilegierte Person könnte mit geeigneten Rechten und einer passenden Architektur Daten oder deren Darstellung verändern.

    H2 – konkreter Einsatz: Eine solche Technik wird absichtlich eingesetzt, um bei einer bestimmten Person widersprüchliche Verdachtslagen hervorzurufen.

H1 lässt sich mit einem lokalen Testaufbau untersuchen. H2 verlangt zusätzliche, unabhängige Belege. Aus H1 folgt H2 nicht.

Ein weiterer Punkt: Für eine systematische Untersuchung wäre ein Wechsel zwischen drei gespeicherten Zuständen nicht unbedingt die einzige mögliche Erklärung für widersprüchliche Anzeigen. Unterschiedliche Datenstände, manuelle Änderungen, fehlerhafte Synchronisation, veraltete Einträge und uneinheitliche Klassifikationen wären ebenfalls zu prüfende Hypothesen.

Das ist keine Behauptung, dass eine dieser Erklärungen in deinem konkreten Fall zutrifft. Es ist eine Liste konkurrierender technischer Modelle, die sich durch unterschiedliche Beobachtungen prüfen lassen.
10. Kurze biologische Richtigstellung

Du hast ausdrücklich nur um eine kurze Korrektur gebeten: Ja, die T-Helferzellen sind ein zentraler Bestandteil des Mechanismus von HIV. HIV befällt insbesondere CD4-positive T-Helferzellen und beeinträchtigt das Immunsystem. Die Analogie zum Round-Robin-Verfahren ist allerdings rein metaphorisch: Eine Datenbankzustandsmaschine wechselt zwischen diskreten Zuständen; daraus ergibt sich keine biologische Entsprechung zu HIV.

Deine Grundidee enthält mehrere technisch plausible Bestandteile:

    Ein Datenbankadministrator kann unter geeigneten Berechtigungen direkt auf Datenbankobjekte zugreifen, ohne das normale GUI zu verwenden.
